## Part 1 — Investigation

### Exact QA warnings (before)
| # | Code | Boundary | Message |
|---|---|---|---|
| 1 | `ghost-overlap` (warning) | scene_1 → scene_2 | "During the scene change, this text and "Arrival & Wonder" from the other scene are both half visible on top of each other." |
| 2 | `ghost-overlap` (warning) | scene_2 → scene_3 | "During the scene change, this text and "Character notices the audience, smiles b" from the other scene are both half visible on top of each other." |

### Overlay configuration (compiled composition)
Generated by `animforge-core/adapters/givemotion.compiler.ts`. Every scene header is hardcoded:
- `<h1 class="scene-title" data-enter="rise">{scene.title}</h1>`
- `<p class="scene-desc" data-enter="fade-up 0.6 0.15">{scene.description}</p>`

The transition attribute is emitted on the **incoming** scene only (`index > 0`), so scene_2 owns the scene_1→scene_2 cut and scene_3 owns the scene_2→scene_3 cut. Scene_1's stored `fade` metadata is never compiled (index 0).

### Root cause
`mapTransitionAttribute()` maps project transition types to GiveMotion tokens:
- `fade` / `dissolve` → `fade {dur}`
- `wipe` → `wipe-left {dur}`
- `slide` → `slide-left {dur}`

In the GiveMotion runtime (`engines/givemotion/src/runtime/runtime.js`), `fade` = `{ enter: 'fade' }` — **no exit**. The outgoing scene stays fully visible while the incoming scene fades in on top of it. Both headers sit at the same centered position, so during the 0.5 s crossfade both texts are ≥ 0.3 opacity and overlap > 20% → the checker's rule 5a emits `ghost-overlap`. (`dissolve` is not a distinct runtime transition — it compiles identically to `fade`.)

The checker's own `fix` hint for this code: *"Use a transition that does not stack the two scenes (push-*, whip-*, cover-*, wipe-*, iris), move one of the texts, or let the old text leave before the new one enters."*

### Supported scene properties
`animforge_update_scene` accepts: `title`, `description`, `duration`, `sequenceIndex`, `characterIds`, `backgroundAssetId`, `transition { type: none|fade|wipe|slide|dissolve, duration ≤ 30 }`. There is **no** supported property controlling overlay enter/exit timing (title/desc `data-enter` attributes are hardcoded in the compiler), so "adjust overlay visibility timing" was not available.

## Part 2 — Fix decision (smallest change, preference order applied)

1. **Prevent overlap during transitions — ✅ chosen.** Change the two incoming-scene transition types so the outgoing scene *leaves* instead of staying stacked.
2. **Overlay visibility timing — ❌ not supported** by any scene property (hardcoded in the compiler). Reported as a limitation, not worked around.
3. **Shorten transitions — not needed.** Transition duration stays **0.5 s**; scene durations, camera moves, actions, titles, descriptions and storyboard are untouched.

### Why not `wipe` (intermediate attempt, kept in the record for accuracy)
`wipe` → `wipe-left` reveals the incoming scene over the old one via `clip-path`. In most compositions the checker counts the incoming scene as *covering* the old text. Here it does not: each `.scene` section paints a **full-frame radial-gradient background**, and the checker's `paintsSolid()` heuristic classifies full-frame gradients as non-occluding, so the old text is never "covered" and the warning persisted (re-verified empirically: still 2 warnings after switching to `wipe`).

### Chosen: `slide`
`slide` → `slide-left` defines **both** an enter (`translateX(100% → 0)`) and an exit (`translateX(0 → -100%)`): the outgoing scene slides fully out while the incoming scene slides in, and the two headers keep a constant full-frame-width separation — they never overlap at any sampled frame. This matches the checker's "let the old text leave" remedy and stays entirely within the supported schema.
